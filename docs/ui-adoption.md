# Vibers Admin UI adoption

## 기본값

바이퍼스 어드민의 기본 UI 방향은 `aceternity`로 기록한다. 이는 Aceternity의 예제 코드를 모든 앱에 복사한다는 뜻이 아니라, 다음 구조를 공통 계약으로 사용한다는 뜻이다.

- 접을 수 있고 스크롤이 독립적인 왼쪽 업무 메뉴
- 고정 상단바의 프로필·알림·현재 프로젝트 정보
- 넓은 본문과 선택적인 오른쪽 보조 패널
- 요약 카드 → 추이 그래프 → 작업 목록 순서의 정보 위계
- 카드·테이블·필터·드로어·토글의 일관된 상태 표현
- 키보드 포커스, 모바일 메뉴, 빈 상태와 오류 상태를 기본 제공

시각적 기준은 토스 비즈니스 관리자처럼 정보 밀도를 낮추고, 업무 결정을 빠르게 하는 방향으로 잡는다. 토스의 마크업이나 CSS를 복사하지 않는다.

## 적용 경계

### Next.js / React

`src/ui/tokens.ts`와 `src/ui/admin-shell.css`를 기준으로 AdminShell, Sidebar, Topbar, StatCard, ChartCard, DataTable을 프로젝트 안에 얇은 어댑터로 구현한다. Aceternity 컴포넌트는 카드·그래프·드로어처럼 상호작용이 필요한 화면에만 선택한다.

### Rails

React를 도입하지 않는다. CSS 변수와 HTML partial로 같은 shell·카드·테이블 구조를 구현하고, Rails의 인증·권한·폼 흐름은 그대로 유지한다.

### Expo / React Native

웹 DOM이나 CSS를 복사하지 않는다. 토큰의 색상·간격·radius·상태 체계만 NativeWind/StyleSheet로 매핑한다.

### PHP / WordPress

관리자 전체를 교체하지 않는다. 업무상 필요한 대시보드 카드와 표부터 HTML/CSS로 단계 적용한다.

## 안전한 적용 순서

1. 공통 토큰·shell 계약을 태그로 고정한다.
2. Exact Vibers Ops를 기준 구현으로 검증한다.
3. 팬이지는 현재 변경분이 정리된 별도 브랜치에서만 적용한다.
4. 프로젝트별로 한 화면씩 적용하고, 각 저장소의 기존 테스트를 먼저 통과시킨다.
5. 프로젝트별 커밋과 배포 검증을 분리한다. 공통 저장소의 변경을 자동으로 전 프로젝트에 밀어 넣지 않는다.

## 금지사항

- Aceternity 토큰 또는 다른 비밀값을 클라이언트 번들에 넣지 않는다.
- 고객용 랜딩 페이지에 어드민 shell을 강제하지 않는다.
- 기존 프로젝트의 미커밋 변경을 포함하거나 정리하지 않는다.
- 화면 통일을 이유로 프로젝트별 권한·데이터 경계를 합치지 않는다.
